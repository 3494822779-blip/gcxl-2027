# Jetson ↔ 下位机串口协议

本文供下位机固件开发和整机联调使用，按 2026-11-06 工作空间代码与配置整理。协议是 ASCII 行协议，不是二进制结构体。

实现依据：

- [actuator.py](../ros2_ws/src/block_perception/block_perception/actuator.py)：控制帧编码、反馈校验、角度与执行状态。
- [serial_node.py](../ros2_ws/src/serial_minimal/serial_minimal/serial_node.py)：串口收发与换行。
- [nodes.py](../ros2_ws/src/block_perception/block_perception/nodes.py)：视觉对准、前进和抓取条件。
- [perception.yaml](../ros2_ws/src/block_perception/config/perception.yaml)：本项目参数。

本文的“当前配置”指上述 YAML 中的数值。启动时可通过其他 YAML 或运行时参数覆盖；Python 类的内置默认值与项目 YAML 并不完全相同，以实际运行参数为准。

## 1. 通信方向与职责

| 方向 | 帧类型 | 用途 |
|---|---|---|
| Jetson → 下位机 | `$CMD` | 两轮速度、两夹爪绝对角度、相机绝对俯仰角 |
| 下位机 → Jetson | `$FB` | 相机当前俯仰角反馈 |

上位机链路：

```text
alignment/command + gripper/angles
    → actuator → /serial_tx → serial_node → 串口 → 下位机
下位机 → 串口 → serial_node → /serial_rx
    → actuator 校验和解析 → /camera/joint_states → alignment
```

`CMD` 不是反馈帧。下位机把收到的 `CMD` 原样回传，不会更新上位机的实际角度。协议目前没有 ACK、重传、轮速反馈、底盘里程计或夹爪到位反馈；成功写入串口也不等于下位机已经执行。

## 2. 串口与分帧

| 项目 | 约定 |
|---|---|
| 当前设备 | `/dev/ttyACM0`，由 `serial_node.port` 设置 |
| 当前波特率 | 115200，由 `serial_node.baud` 设置 |
| 串口格式 | 8 数据位、无校验位、1 停止位，raw 模式，无软件流控；设备端关闭硬件流控 |
| 编码 | ASCII |
| 行结束 | 必须有 LF（字节 `0x0A`）；可接受 CRLF |
| 数字 | 十进制，小数点为 `.`，不带单位或字段名 |

一帧格式：

```text
$<body>*<HH>\n
```

其中 `HH` 为两位十六进制 XOR 校验。本文代码块里的 `\n` 表示真正的换行字节，不是反斜杠和字母 n。串口没有消息边界，一次读取可能得到半帧或多帧，下位机必须缓存后按 LF 拆行。

上位机 `/serial_tx` 消息本身不含换行，`serial_node` 写入串口时追加 LF。`/serial_rx` 是原始数据块，不能假定一个 ROS 消息就是一帧；`actuator` 按 LF 重组，接收缓存最多保留 512 个字符。

## 3. XOR 校验：仅计算 `$` 与 `*` 中间的内容

计算规则：初值 `0x00`，对 body 的每一个 ASCII 字节依次异或，包括字母、逗号、数字、小数点及负号。**不包含 `$`、`*`、校验文本、CR、LF，也不包含字符串末尾的 NUL。**

例如：

```text
完整帧：$FB,0,0.000*1A\n
参与校验：FB,0,0.000
```

校验使用实际发送的文本。`0.0` 和 `0.000` 虽然数值相同，校验不同；先格式化全部字段，再对该字符串计算校验。上位机发送大写十六进制，反馈解析接受大小写，但必须恰好两位。

### 3.1 已核验的反馈样例

| body | 正确校验 | 正确帧（末尾另加 LF） |
|---|---|---|
| `FB,0,0.000` | `1A` | `$FB,0,0.000*1A` |
| `FB,1492,0.000` | `24` | `$FB,1492,0.000*24` |

本次日志出现过错误帧 `$FB,0,0.000*30` 和 `$FB,1492,0.000*0E`。错误校验分别满足 `0x1A XOR 0x2A = 0x30`、`0x24 XOR 0x2A = 0x0E`，其中 `0x2A` 是 `*`。这提示应检查固件是否把 `*` 算进了校验；仅凭该差值不能证明固件具体实现。

### 3.2 C 发送参考代码

下面构造完整反馈帧。调用者负责把返回的字节数全部发送，包括 LF；串口 API 若可能部分写入，应继续发送剩余字节。

```c
#include <stdint.h>
#include <stddef.h>
#include <stdio.h>
#include <math.h>

static uint8_t xor_body(const char *body, size_t len) {
    uint8_t value = 0;
    for (size_t i = 0; i < len; ++i) {
        value ^= (uint8_t)body[i];
    }
    return value;
}

/* 返回帧长度；失败返回 -1。嵌入式 printf 需支持浮点格式化。 */
static int make_feedback(char *out, size_t capacity,
                         uint16_t seq, float measured_pitch_deg) {
    if (!isfinite(measured_pitch_deg)) return -1;
    char body[64];
    int n = snprintf(body, sizeof(body), "FB,%u,%.3f",
                     (unsigned)seq, (double)measured_pitch_deg);
    if (n < 0 || (size_t)n >= sizeof(body)) return -1;
    uint8_t check = xor_body(body, (size_t)n);
    int total = snprintf(out, capacity, "$%s*%02X\n",
                         body, (unsigned)check);
    if (total < 0 || (size_t)total >= capacity) return -1;
    return total;
}
```

接收 `CMD` 时先定位 `$` 与 `*`，对两者之间的原始文本校验，再解析数值；不要把数值重新格式化后用于验证收到的校验。

## 4. 上位机发送：CMD

```text
$CMD,<seq>,<lw>,<rw>,<lg>,<rg>,<cp>*<HH>\n
```

body 按逗号分割恰好 7 项：`CMD` 加 6 个字段。正常运行目标频率 20 Hz（每 50 ms），调度可能有抖动。退出时会另外尝试发送多帧停车命令。

| 字段 | 格式 | 含义 |
|---|---|---|
| `seq` | 整数 0～65535 | 上位机序号，循环递增；节点重启从 0 开始 |
| `lw` | 3 位小数 | 左轮速度原始值，正为前进、负为后退 |
| `rw` | 3 位小数 | 右轮速度原始值，正为前进、负为后退 |
| `lg` | 1 位小数 | 左夹爪绝对目标角度，单位度 |
| `rg` | 1 位小数 | 右夹爪绝对目标角度，单位度 |
| `cp` | 1 位小数 | 相机绝对目标俯仰角，单位度 |

### 4.1 轮速单位与方向

```text
串口轮速原始值 = 物理轮速(m/s) × wheel_speed_scale
```

当前 `wheel_speed_scale=100.0`，所以 0.5 m/s 对应 `50.000`，不是 `500.000`。当前 `max_wheel_speed=0.5`，正常控制输出范围是每轮 `[-50, 50]`。下位机必须与此缩放约定一致，不能直接把字段默认解释为 PWM、rpm 或 mm/s。

- 两轮同为正：前进；同为负：后退。
- `rw > lw`：向左转；`lw > rw`：向右转（按车体向前的轮速正方向）。
- `lw=-17, rw=17`：原地左转；`lw=17, rw=-17`：原地右转。
- 电机镜像安装、接线方向修正由下位机完成。

视觉跟踪时上位机已完成差速计算和限幅，当前最小转向分量为每轮 0.17 m/s，即原始值 17。丢弃任务也通过相同字段输出轮速。

### 4.2 舵机字段是绝对角度

`lg`、`rg`、`cp` 都是目标位置，不是速度、增量或 PWM 脉宽。

- 连续收到 `cp=-15.0`，应保持同一个目标，不能每帧再向下转 15°。
- `cp=0.0` 表示相机回正，不表示“停止输出 PWM”。
- 相机正角抬头，负角低头；下位机负责映射到实际舵机零点、方向及脉宽。
- 左右夹爪都以数值增大表示向外张开，镜像安装由下位机转换。目前上位机发送 `lg=rg`。
- 相同目标仍会周期重发，用于持续控制和通信保活；不要每帧重置舵机控制器或轨迹起点。

| 控制量 | 当前 YAML 配置 | 备注 |
|---|---|---|
| `lg`、`rg` | 0～90° | 初始/合拢为 0°，张开上限 90° |
| `cp` | −15～75° | 以实物机械极限校准，下位机仍须限幅 |
| 抓取相机目标 | −15° | `grasp_pitch_deg` |
| 相机回正 | 0° | `pitch_home` 是 ROS 内部弧度参数 |

下位机应对全部字段完成校验、类型检查和有限数值检查后，一次更新整组目标。坏帧不能只执行其中部分字段，也不能刷新有效控制帧的超时计时器。夹爪限流、堵转保护和机械限位由下位机实现。

### 4.3 完整 CMD 样例

以下校验按原样文本计算，发送时末尾追加 LF。运动样例仅用于受控联调，重复发送会持续执行目标。

| 含义 | 完整帧 |
|---|---|
| 轮停、舵机回初始位置 | `$CMD,0,0.000,0.000,0.0,0.0,0.0*54` |
| 以 0.1 m/s 前进 | `$CMD,1,10.000,10.000,0.0,0.0,0.0*55` |
| 轮停、两爪张开 60° | `$CMD,2,0.000,0.000,60.0,60.0,0.0*56` |
| 轮停、相机低头到 −15° | `$CMD,3,0.000,0.000,0.0,0.0,-15.0*4E` |

## 5. 下位机发送：FB

```text
$FB,<seq>,<pitch_deg>*<HH>\n
```

body 恰好 3 项。建议下位机按 20 Hz 或更高频率周期发送，即使角度没变也继续发送，不能只在舵机运动时上报。

| 字段 | 约定 |
|---|---|
| `seq` | 下位机独立整数序号，建议 0～65535 循环；不必与 CMD 相同 |
| `pitch_deg` | 相机当前角度，单位度；与 CMD 的 cp 使用相同零点、正负方向 |

当前上位机不使用反馈序号去重或判断先后，也不要求它与控制帧匹配。接收到合法帧后，将角度从度转为弧度，发布 `/camera/joint_states`，关节名 `camera_pitch`。

反馈应代表实际位置。只有目标值而没有位置测量时，不能把目标原样回传并声称已经到位。若硬件只能提供位置估计，需明确其误差与延迟，不能据此保证真实到位。

合法反馈要求：

1. 有 `$`、`*` 和行结束 LF。
2. XOR 正确，校验文本为两位十六进制。
3. 类型为 `FB`，字段数正确。
4. 序号可解析为整数，角度可解析为有限浮点数；NaN 和无穷大不接受。

当前反馈解析器不校验角度机械范围，也不验证序号范围，固件应自行保证数据合理。反馈无效时上位机不更新角度和接收时间，不发 ACK/NACK。

## 6. 反馈如何影响前进与抓取

当前 YAML 中 `alignment.camera_servo` 与 `actuator.camera_servo` 都为 `true`，两处必须一致。

### 6.1 舵机模式的前进条件

正常视觉跟踪时，前进要求同时满足：

- 目标有效、已锁定且未过期。
- 实际俯仰反馈未过期，当前 `pitch_timeout=0.25 s`。
- 实际俯仰角 `pitch > grasp_pitch`，当前 `grasp_pitch=-0.26 rad`（约 −14.90°）。
- 目标水平误差不超过 `forward_max_error_x=0.3`，且尚未发出抓取请求。

因此流程是“反馈有效且相机尚未低到抓取角时，边前进边调整”。不是等相机到位才允许前进。没有合法反馈时，前进被禁止；转向和视觉俯仰调节仍可能有输出，不代表所有执行器都停了。

上位机根据视觉误差计算俯仰速度，再积分成 `cp`，最后限幅。反馈缺失本身不能证明 cp 一定持续下降；方向取决于误差和增益，发送目标角与实际角度也不能混为一谈。

### 6.2 抓取与后续动作

正常视觉抓取请求还要求水平、垂直误差到位，目标为真实观测、俯仰反馈新鲜且达到抓取角，并保持 `hold_seconds`（当前 0.3 s）。

`actuator` 进入抓取阶段后：

1. 两轮速度为零，发送 `cp=grasp_pitch_deg`（当前 −15°）。
2. 等待有效反馈满足 `abs(实际角 - 抓取目标角) <= grasp_pitch_tol`。
3. 当前容差为 0.06 rad，约 **3.44°**；符合条件后夹爪合拢到 0°。
4. 等待 `claw_settle_sec`（当前 0.5 s）；这是计时等待，不是夹爪到位反馈。
5. 普通任务当前 `discard_enabled=true`，随后自动丢弃；关闭此选项时进入完成状态。首抓任务另按任务标记决定后续动作。

丢弃复用 CMD：左转约 90° → 张爪 90° → 后退 → 再保持张爪 → 前进 → 右转约 90° → 停车。当前前后移动距离为 0.2 m。底盘动作依赖时间估算，没有里程计闭环，结束时夹爪保持张开。不能假定“抓取完成后永远不松爪”。

丢弃/完成状态会命令相机回正。当前实现没有用 `pitch_home_tol` 等待相机实际回正后再开始丢弃动作。

### 6.3 固定相机模式

两处 `camera_servo=false` 时，前进依据视觉框下边缘位置，不依赖俯仰反馈；`cp` 持续发送 `camera_fixed_deg`（当前 0°），不会因此停止发送相机字段。固定模式仍可解析合法 FB，但控制决策不依赖它。

## 7. 超时、重启和退出

以下是下位机必须实现的控制约定，ROS 串口桥不会代替固件执行：

- 上电及首帧前：轮速为零，舵机采用已标定的初始位置（相机回正、夹爪 0°）。
- 超过 250 ms 没有合法 CMD：两轮停车，相机和夹爪保持，不强制回零。
- 再次收到合法 CMD：更新完整控制目标并恢复计时。
- 序号回绕或上位机重启后从 0 开始，不应导致永久拒收。

正常跟踪阶段视觉指令丢失/过期时，上位机发送零轮速并保留舵机目标；已经启动的抓取或丢弃任务有自己的执行状态，不能假定此时丢失视觉会终止任务。

正常 Ctrl+C 退出时，上位机尝试连续发 5 帧停车命令，舵机保持最后目标；进程崩溃、断电、USB 断线时不保证能发出，仍依赖下位机超时停车。

## 8. 联调与日志

### 8.1 只运行一套控制节点

不要同时运行多个 perception/first_grasp 启动实例，也不要让串口助手或独立测试脚本与 serial_node 同时占用串口。重复实例可能争用相机、重复发布控制命令或争抢串口接收数据。

```bash
fuser -v /dev/video0 /dev/ttyACM0
ros2 node list
ros2 topic info /serial_tx --verbose
```

### 8.2 启动并记录实际收发

在项目根目录执行：

```bash
source /opt/ros/humble/setup.bash
source ros2_ws/install_gcxl/setup.bash
BP_DEBUG=actuator ros2 launch block_perception perception.launch.py camera:=true serial:=true
```

另一个已加载 ROS 环境的终端查看：

```bash
ros2 topic echo /serial_tx
ros2 topic echo /serial_rx
ros2 topic echo /camera/joint_states
ros2 topic echo /alignment/command
```

上述 echo 命令分别运行，或退出上一条后运行下一条。

详细日志默认在 `~/.ros/block_perception_debug/actuator.jsonl`，可用 `BP_DEBUG_DIR` 改目录。默认不开启；普通 ROS 日志没有 `rx_feedback` 不能证明没有反馈。日志文件会追加并轮转，分析时必须核对时间，不能拿旧记录判断本次状态。

| 事件/字段 | 含义 |
|---|---|
| `tx_command` | 发布到 ROS 的 CMD，约每 0.5 s 记录一次；不等于逐帧硬件发送证明 |
| `rx_feedback` | 成功解析 FB，约每 0.5 s 记录一次 |
| `rx_bad_frame` | 非空行解析失败，约每 1 s 记录一次；检查类型、校验、字段 |
| `pitch: null` | 此 actuator 实例尚未获得有效俯仰角 |
| `pitch` 数字 | 最近接收角度，单位弧度；单独有数值不证明它仍新鲜 |

`/camera/joint_states` 也可能由其他节点发布，若判断串口反馈来源，应结合 `rx_feedback` 与发布者信息。

### 8.3 独立串口检查

先停止 ROS 串口节点及其他占用串口的软件，再在项目根目录执行：

```bash
python3 scripts/serial_check.py --port /dev/ttyACM0
```

脚本会发送 CMD 并检查反馈，默认轮速零、夹爪和相机目标为零，舵机可能回到初始位置。只检查能否打开及写入串口可加 `--tx-only`，但通过不证明下位机收到或执行。

## 9. 常见问题定位

| 现象 | 检查顺序 |
|---|---|
| 有 FB 文本但 `pitch:null` | 看 rx_bad_frame；核对 XOR 是否包含了 `*`、字段数量和 LF |
| 相机不到位、车不前进 | 先确认反馈合法且小于 0.25 s；再看目标有效性、水平误差和实际角是否已过抓取阈值 |
| 相机一直往一个方向 | 同时比较 CMD 的 cp、FB 实际角和视觉 pitch_rate；检查角度增量误解、正负方向及零点 |
| cp 始终为 0 | 检查 actuator 是否固定相机模式、指令是否有效、pitch_rate 是否为零；不能只归因于反馈 |
| cp 不变但舵机抖动 | 排查多个发送者、下位机重复重置轨迹、PWM、供电和机械负载；恒定指令不能单独证明某个原因 |
| 有 CMD 但车轮不动 | 先看 lw/rw 是否为零；非零再查缩放、固件解析、电机控制与供电 |
| 相机启动失败 | 先查相机占用、设备路径和驱动日志；不能仅由串口接入推断 USB 供电冲突 |

## 10. 固件交付核对

- CMD 的 6 个字段顺序正确，轮速缩放与本机配置一致。
- 舵机角度按绝对目标执行，0°语义和正负方向一致。
- FB 使用真实位置或明确说明的位置估计，周期至少 20 Hz。
- XOR 仅覆盖 body，两位十六进制，结尾发送真实 LF。
- 支持拆包、粘包，坏帧不执行、不刷新控制超时。
- 250 ms 控制超时停车，舵机保持；重启和序号回绕可恢复。
- 本文与固件、上位机协议实现一起维护；参数修改后重新核对范围和单位。
