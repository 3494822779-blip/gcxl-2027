# 智能救援比赛策略大纲

本文作为后续策略算法的设计参照，基于 2026-11-08 的现有代码（提交 `ab9d429`）及官方规则文档第 14～19 页截图编写。本文不是运行配置，修改本文不会改变机器人行为；新增策略与接口需另行实现、验证。

## 1. 策略目标与范围

在比赛时间内，将允许搬运的救援目标送入指定救援区域，优先保证首次目标要求、有效得分和任务完成率，再优化单轮耗时。策略基本循环为：观察 → 选择 → 必要清障 → 抓取 → 搬运 → 投放 → 确认 → 再次观察。

现阶段首先完成“可靠选块、抓取和保持”的局部闭环；回收区导航、定点投放与完整比赛循环属于后续开发范围。不能将目前的“抓取后丢弃”视为比赛救援完成。

## 2. 比赛规则依据

以下依据官方规则文档第 14～19 页整理。第 19 页只说明初赛按“评分规则”计算，具体分值和比赛时长不在这几页内，须与完整评分规则核对。未核实的内容不能直接变成控制常量。

**目标分类（第 17 页）：**

| 目标 | 外形 | 数量 | 模型类别 | 搬运约束 |
|---|---|---|---|---|
| 普通物资 | 绿色 40mm 正方体 | 8 | `class_0` | 首件必须是它，且首趟只运 1 个 |
| 核心物资 | 黑色 40mm 正三棱锥 | 4 | `class_1` | 得分目标；可与普通物资混运 |
| 伤员 | 橙色 80×40×40mm 长方体 | 4 | `class_2` | 必须单独运，一次 1 个 |
| 危险目标 | 浅蓝色 40mm 正方体 | 4 | `class_3` | 不得运入安全区 |

类别映射来自标签与目标颜色的对应推断（绿、黑、橙、蓝），上机前须用实物验证，通过后才能启用类别筛选。

**规则摘要：**

| 项目 | 规则摘要 | 对策略的约束 |
|---|---|---|
| 首次搬运 | 第一次必须单独运 1 个普通物资进安全区的物资区，一次运多个无效（第 18 页） | 首次抓取完成不等于首次搬运完成，需确认首件有效入区后再放开后续搬运 |
| 单趟数量 | 首趟之后每趟最多 3 个，超过无效；伤员须单独运 | 状态机须支持持多件，伤员独占 |
| 无效目标 | 运入安全区但无效的目标会被取出，重新随机放到场地中央 | 误运不损失目标，但浪费时间 |
| 计分 | 以最后留在安全区的目标数量为准（第 19 页）；分值待核对 | 得分以有效入区为依据，不能按合爪次数累计 |
| 场地 | 3000×3000mm，安全区约 600×300mm，在场边中央，分物资区和伤员区各占一半 | 不同类别要送到对应的一半，不能笼统视为同一放置区 |
| 对手 | 两台机器人同时比赛；不得进入对方安全区，不得把目标推入对方安全区；违规可能直接结束比赛 | 路径规划要考虑对手；需有碰撞保护 |
| 机器人 | 尺寸不超过 300×300×200mm，重量不超过 1.5kg | 车体、夹爪和目标的空间余量要按此估算 |
| 禁止行为 | 不得损坏目标、不得将目标放在机器人上；不得用推、摩擦方式处理目标 | 采用抱住搬运；不能把推进障碍当作清障 |

**优先核实事项：**比赛时长和各类分值（第一张 PPT 截图中的 100 秒、5/10 分及扣分数值未在官方文档这几页中找到）、安全区内物资区与伤员区的精确边界、出界及碰撞判罚、清障物允许放置位置、危险目标的扣分规则。

## 3. 现有能力与边界

| 能力 | 当前已实现 | 策略使用边界 |
|---|---|---|
| 检测与跟踪 | YOLO/TensorRT、NvDCF；输出框、类别、置信度、跟踪编号和真实观测标记 | 只有图像坐标，不是场地坐标或可靠距离 |
| 普通目标选择 | 优先选框下边缘最低的真实目标，并持续锁定 | 不按比赛得分、颜色或指定区域选块；不能直接实现高分优先 |
| 对准与接近 | 水平对准、靠近、相机俯仰调节、按框宽预张爪 | 短时预测可辅助对准，不能凭预测触发抓取 |
| 抓取 | 停车、相机低头到位、合爪等待、发出相机回正指令 | 成功表示动作流程完成，没有物块在爪确认 |
| 首次抓取 | 仅以 `class_0` 为正式目标，可循环抓取并丢弃遮挡物 | 属于当前任务约定，不代表已满足比赛首件入区规则 |
| 丢弃 | 左转 90°、开爪、后退、再次开爪、前进、右转 90° | 固定相对动作；不识别放置区，不确认落点，不保证准确回原位 |
| 基础运动 | 按距离直行、按角度转向 | 依靠速度与时间估算，没有里程计闭环 |
| 任务记忆 | 记录任务、抓取、丢弃、取消和超时 | 仅本进程内存；重启清空，不是地图或真实持物证明 |
| 全场策略 | 尚未实现 | 定位、导航、区域识别、避障、持物确认、有效投放和计分均需补齐 |

模型实际标签仅为 `class_0`～`class_3`，见 [模型说明](../models/yolov8n_gcxl_aug/README.md)。当前约定为 `class_0` 绿色普通物资、`class_1` 黑色核心物资、`class_2` 橙色伤员、`class_3` 浅蓝危险目标（见第 2 节）。该映射尚未经实物验证，验证后才启用比赛类别筛选。尤其需要确认 `class_0` 与首次允许搬运的普通物资一致，以及 `class_2` 能覆盖长方体的各种朝向。

## 4. 分阶段实现路线

### 阶段一：局部抓取基线

1. 使用普通模式且设置 `autonomous:=false`，由上层策略独占动作调度。
2. 调用 `approach_grasp`，明确设置 `discard_after: false`。
3. 抓取流程结束后停车保持，读取记忆，区分“已发出抱住指令”和“实物确认已抱住”。
4. 验证丢目标、反馈过期、取消、超时及再次触发不会导致重复动作。

该阶段验证动作链路，不宣称完成比赛搬运。

### 阶段二：首次抓取与清障

1. 独立启动 `first_grasp.launch.py`，发送 `first_grasp`。
2. 现有逻辑在 `class_0` 左右边缘之间、框顶部到画面顶部的区域检查 `class_1` 相交；优先选择没有前方遮挡的合格目标。
3. 前方遮挡按横向相交且框下边缘更低近似判断；清障结束必须获取新图像重新选择。
4. 正式抓取完成后保持抱住，转入后续搬运状态，而非宣布首次救援完成。
5. 现有筛选的实际行为（见 `first_grasp.py`）：目标上方条带内与 `class_1` 相交时，该 `class_0` 目标被跳过，不会清障；目标正前方（横向相交且框下边缘更低）最近的已观测框会成为清障对象，不限类别，可能是 `class_0`、`class_1`、`class_2` 或 `class_3`。因此得分目标可能被当作障碍丢弃。丢弃是抱住后放到一旁，目标仍在场上，不算损失，因此不必按类别禁止。比赛启用前须补的是：落点合法性（不出界、不进对方安全区、不挡后续路线）、次数和时间预算；条件未满足时不启动该任务。优先换目标，没有无遮挡目标时才清障。
6. 目标上方条带内回避 `class_1` 的原始设计意图在代码中未注明。`class_1` 现按规则对应黑色核心物资，该回避是否仍有必要，需与设计者确认后再决定保留或调整。

普通模式与首次抓取模式是互斥入口。当前首次模式不能直接执行 `align`、`approach_grasp`，普通模式不能执行 `first_grasp`；未来统一比赛循环须先设计选目标模式切换和控制权交接，不能同时启动两套节点竞争底盘。

### 阶段三：单件搬运闭环

补齐定位、目标放置区识别、路线执行、持物与落点确认，实现一次“抓取 → 回收区 → 释放 → 脱离 → 有效入区确认”。初期使用已标定、无遮挡路线验证；时间控制运动只能作为基础动作，不能充当可靠位置反馈。

### 阶段四：完整比赛调度

加入首件入区解锁、收益选块、受限清障、剩余时间管理、失败恢复和循环搬运。高分目标策略应在基础闭环稳定后启用。

## 5. 建议的上层状态机（待实现）

| 状态 | 行为与进入条件 | 离开条件 |
|---|---|---|
| `WAIT_START` | 自检、确认模式与类别映射，底盘停车，等待比赛开始信号 | 收到有效开始信号，启动比赛时钟 |
| `OBSERVE` | 获取新鲜检测、任务记忆、位置与持物状态 | 信息充分进入选择；数据异常进入恢复 |
| `SELECT` | 首件未有效入区时只选 `class_0` 且本趟只运 1 个；之后每趟最多 3 个，伤员（`class_2`）单独成趟，`class_3` 不选；按收益选择 | 目标及路线可行则接近，需清障则先评估清障 |
| `CLEAR` | 仅在清障合法、落点可用且时间足够时执行 | 完成后回到观察；达到上限则换目标或停止 |
| `APPROACH_GRASP` | 锁定目标、对准并抓取，禁止正式目标自动丢弃 | 动作结束后进入持物确认；失败进入恢复 |
| `VERIFY_HOLD` | 使用未来补充的视觉或传感器检查实物 | 确认抱住进入搬运；无法确认则记录未知并恢复 |
| `TRANSPORT` | 保持抱住，沿验证过的路线进入目标放置位置 | 到位且允许释放；位置不确定则恢复 |
| `PLACE` | 停车后开爪，按可行路径脱离目标 | 释放与脱离流程完成后检查落点 |
| `VERIFY_PLACE` | 检查物块完全入区、类别及必要朝向 | 确认有效才登记救援；首件有效后进入多件搬运（单趟不超过 3 个，伤员除外） |
| `RECOVER` | 取消当前动作，等待终态，重新观察并评估持物、位置和时间 | 有可验证恢复方案则继续，否则停止 |
| `FINISH` | 取消未完成动作并停车，不自动释放未知位置的目标 | 保持终止状态，等待下一轮明确初始化 |

现有 Action 一次只抓一个目标，抓取后再次抓取会把上一个持物状态置为未知（`uncertain_hold`），记忆里也没有“持有几件”的计数。多件搬运要先补持物计数与确认，在此之前只能按单件循环设计。

“定位完成”“抱住确认”“投放成功”等是未来状态机的输入条件，目前没有对应完整实现，不允许用固定等待直接替代确认。

## 6. 选目标与清障策略

### 6.1 先过滤，再排序

过滤掉非真实观测、过期数据、类别未知、规则不允许、路线不可行和无法在剩余时间内完成的目标。首件入区前只开放普通物资（`class_0`）；危险目标（`class_3`）不进入搬运候选；伤员（`class_2`）只能单独运，不与其他目标混运；每趟最多 3 个。

在合法候选中，建议以“预计有效得分 / 预计总耗时”为主要排序指标，并考虑成功概率、清障成本和违规风险。总耗时包含接近、清障、抓取、搬运、释放及验证，不能只估算到达物块的时间。

初期采用容易调试的顺序：无遮挡且易抓 → 路线短且投放简单 → 预计单位时间收益高。分值及概率未知时不编造精确收益；先积累实车数据。当前普通选择器仍按框下边缘排序，实现上述策略需要扩展选择器及目标交接接口，现有 Action Goal 没有指定 `track_id` 或 `class_id` 的字段。

### 6.2 锁定与失败目标

- 接近期间保持锁定，避免候选排序变化导致来回换目标。
- 跟踪编号不是永久物块身份；重绑定后重新验证类别、位置和真实观测。
- 同一目标连续失败后，临时降低优先级并重新观察；不能只凭旧编号永久排除实物。
- 无目标先停车等待；主动转向搜索需要新增视野覆盖、场地边界检查和搜索超时。

### 6.3 清障约束

- 清障必须有明确收益：清障后存在可完成的正式目标任务。
- 不清走已经有效入区的目标，不将障碍释放到禁区、边界、对方安全区或后续必经路线。
- 优先换目标，其次才清障。绕行需要场地定位和路径规划，当前没有，不作为选项。
- 任何类别都可以被抱住丢弃，但落点须合法，且 `class_3` 不得被带入安全区。每次丢弃约 6.4 秒（按配置估算，待实车标定），应计入清障成本。抱住 `class_1`（三棱锥）和 `class_2`（长方体，80mm 长边）的可靠性未验证，先实测。
- 设置单目标清障次数上限和累计耗时上限；具体值由实车统计确定。
- 现有 `discard` 含转向和前后移动，必须验证整个动作包络与落点，不能只检查开爪瞬间。
- 清障后重新定位与观察，不能假定车和剩余目标仍处于原位置。

## 7. 时间预算与异常恢复

比赛时钟从规则规定的开始事件计时，动作取消、重试和节点切换均不能重新计时。PPT 截图给出的 100 秒暂作为待核对比赛时长，官方文档这几页未见该数值。

开启新任务的条件：剩余时间大于“预计接近与抓取时间 + 搬运与投放时间 + 确认时间 + 停车余量”。各项用实测保守估计，预留余量和重试次数待标定；时间不足时不再接新目标。已经持物时优先评估能否完成当前合法投放，不能为赶时间盲目开爪。

按现有配置估算（`discard.py`、`perception.yaml`），一次完整丢弃约 6.4 秒：两次 90° 转向各约 0.7 秒，两次 0.5 秒等待，后退和前进各 2 秒。这是纯计时动作，不含接近和抓取。100 秒比赛里每次清障都要占掉这部分，应计入清障成本。

每个 Action 显式设置正的 `timeout_sec`，受阶段预算和全局剩余时间共同限制。当前普通动作默认 60 秒、首次抓取默认 180 秒，不能直接作为比赛调度预算；`timeout_sec: 0` 表示使用默认值，不表示立即超时。

| 异常 | 建议处理 |
|---|---|
| 图像或目标过期 | 停止接近，等新观测；超过阶段预算则取消并重新规划 |
| 相机到位反馈过期 | 不继续合爪，取消后检查反馈链路 |
| Action 被拒绝 | 查询当前任务状态；不并发重发，不直接向底层发布运动指令抢占 |
| 抓取结束但持物不明 | 记录未知；确认后才决定重抓、搬运或恢复 |
| 移动超时、打滑或定位丢失 | 停车并重新定位，不能按指令距离累加为真实位置 |
| 清障反复无效 | 取消当前清障任务，重新选目标或停止；禁止无限循环 |
| 取消、超时或节点重启 | 丢弃未验证的过程假设，检查真实状态；旧记忆不能恢复比赛事实 |
| 比赛截止 | 取消活动 Goal 并等待终态；系统级截止停车与通信故障停车保障需补齐验证 |

## 8. 动作接口与记忆使用约定

统一入口为 `/robot/execute`，类型为 `block_interfaces/action/RobotTask`。上层一次只拥有一个活动 Goal，等待结果后再提交下一步。

| 用途 | 现有调用及注意事项 |
|---|---|
| 普通正式抓取 | `operation: approach_grasp`、`discard_after: false`，仅普通模式 |
| 首次抓取 | `operation: first_grasp`，仅首次模式；可能自动执行清障丢弃 |
| 单独对准 | `operation: align`，不合爪，仅普通模式 |
| 原地抓取 | `operation: grasp`，不负责选目标和接近 |
| 基础行走 | `move` 使用有符号 `distance_m`；`turn` 使用有符号 `angle_deg`，正为左转；`speed_mps` 为速度大小 |
| 区域内释放基础动作 | `claw` 使用 `angle_deg`，只能开爪，不能证明投放有效；手动 `claw` 会把持物状态置为 `unknown`（`manual_claw_command`） |
| 清障丢弃 | `discard` 是固定动作序列，不是导航或定点投放接口 |
| 中断 | 取消当前 Goal，等待终态；忙碌时发送 `stop` 也会被拒绝 |
| 空闲停车 | `operation: stop`，保持舵机目标角度 |

消费 Action 反馈中的 `phase`、`elapsed_sec`、`track_id`、`clearance`，同时检查终态和结果 `success`。`success` 仅表示该动作流程成功，不能单独作为物理抓取、首件入区或比赛得分依据。

现有 `/robot/memory` 提供决策上下文，`/robot/memory/get` 提供完整历史。利用 `session_id`、任务 ID 与抓取记录关联结果；重复通知不能重复计数。`held.state: commanded_hold` 不是实物确认，当前记录的 `physical_confirmed` 不提供真实持物验证。

后续比赛策略需另外维护：比赛开始时刻、首件有效入区标志、类别映射、场地位置及可信度、候选目标失败次数、清障预算、经验证的投放事件与预计得分。新比赛显式初始化；同一比赛内进程重启不能把剩余时间重置或将未知状态当成空爪。

## 9. 开发顺序与验收

1. **规则与标定：**核实类别映射、场地区域、尺寸、投放要求，测量运动和抓取耗时。
2. **上层调度：**实现单 Goal 调度、全局时钟、阶段超时、取消与去重；验证忙碌拒绝、超时和目标丢失。
3. **首件任务：**验证正式抓取与清障记录分离；补齐清障合法性和有界退出。
4. **感知与导航补齐：**实现持物确认、区域定位、路线执行和有效投放确认，完成单件循环。
5. **统一选目标模式：**实现首次与普通策略交接以及类别/目标选择接口，保证控制权唯一。
6. **完整比赛：**验证首件未入区不解锁后续类别，清障与抓取不记救援得分，剩余时间不足不启动不可完成任务。
7. **实车优化：**统计完整循环成功率、每类目标有效得分、清障次数及耗时分布，再调整收益权重。

参数应从 [运行配置](../ros2_ws/src/block_bringup/config/perception.yaml) 与实际执行代码核对。现有行为文档、配置注释和数值存在差异，例如当前右爪闭合为 5°，抓取阶段相机目标为 40°，对准触发阈值 `0.6981 rad` 约为 40°；不能照搬旧文档的角度。对准代码当前满足条件立即触发，不能因配置存在 `hold_seconds` 就假定已执行稳定等待。
